## Stack chosen

No stack existed, so one was chosen to fit `SPEC.md`'s UI requirements (component
library + Radix/shadcn-style primitives, Framer Motion, installable PWA, i18n,
Lighthouse ≥ 90) and its multi-service shape (web app + a separate Python AI service
later). Decisions below are meant to be extended by later tasks, not replaced.

- **Package manager / monorepo**: [pnpm](https://pnpm.io) workspaces. Root
  `pnpm-workspace.yaml` lists `apps/*` and `packages/*`. `packages/*` doesn't exist yet
  — it's reserved for shared code (e.g. the `config/categories` category/quota config,
  once it needs to be imported by both `apps/web` and `services/ai`).
- **Frontend** — `apps/web`: [Next.js 16](https://nextjs.org) (App Router) +
  TypeScript (strict) + Tailwind CSS v4 + ESLint 9 (flat config via
  `eslint-config-next`). Scaffolded with `create-next-app` then trimmed (removed the
  default marketing page/assets, added testing).
  - Tailwind v4 has **no `tailwind.config.ts`** — its config is CSS-native, currently
    a small `@theme inline` block in `apps/web/app/globals.css`. The upcoming "Design
    system: tokens file" task should put the SPEC's design tokens (Ink, Surface, Card,
    Brand, Safe/Target/Reach, Error, fonts, spacing) there, as CSS custom properties
    under `@theme`, with the dark variant under `@media (prefers-color-scheme: dark)`
    (or a `[data-theme]` selector if manual light/dark toggling is wanted later).
  - Testing: [Vitest](https://vitest.dev) + `@testing-library/react` +
    `@testing-library/jest-dom`, jsdom environment. One smoke test
    (`apps/web/__tests__/page.test.tsx`) proves the toolchain end-to-end.
  - `apps/web/CLAUDE.md` and `apps/web/AGENTS.md` are **auto-generated by Next.js 16
    itself** (regenerated by `next dev`/`next build`, per the comment inside them) —
    they are not part of this repo's task-runner instructions and don't override the
    root `CLAUDE.md`. Leave them; don't hand-edit them.
- **Backend / data**: Postgres (via `docker-compose.yml`, task 2) + **Prisma 6.19.3**
  inside `apps/web`, schema at `apps/web/prisma/schema.prisma`, client singleton at
  `apps/web/lib/db.ts`. Pinned to Prisma 6.x deliberately — Prisma 7/8 (the `latest`
  npm dist-tag at the time of writing, itself an RC: `8.0.0-rc.15`) removed the
  `datasource { url = env(...) }` form used here in favour of a `prisma.config.ts` +
  driver-adapter setup; 6.x is the stable, conventionally-documented line and avoids
  building on a moving target for an unattended project. Revisit the pin deliberately,
  not by accident, once 7/8 stabilizes.
  - All 10 SPEC tables exist (College, Course, CollegeCourse, Cutoff, PlacementStat,
    User, AlumniProfile, Message, Report, AuditLog), every one with `source` +
    `isSample` per SPEC.md's literal instruction. For the five in-app tables
    (User/AlumniProfile/Message/Report/AuditLog) `source` defaults to `"app"` and
    `isSample` is expected to always stay `false` — there's no "sample" user content,
    only sample KEA reference data.
  - `User` intentionally has no auth fields yet (no password/session/email) — the
    later "Auth for student/alumni/admin roles with minimal data collection" task
    owns that, in keeping with the minors data-minimisation rule in `CLAUDE.md`.
  - `Cutoff.categoryCode` is a plain string, not a foreign key — `config/categories`
    (a file, per SPEC.md) is the source of truth for valid codes, validated at the
    application layer once that config exists.
  - DB-backed tests (`apps/web/prisma/__tests__/schema.test.ts`) run against a real
    Postgres, not a mock — `make test`/`make check` now depend on `make db-migrate` →
    `make db-up` → `scripts/ensure-db.sh`, which starts the local `postgresql` service
    (or falls back to `docker compose up -d db`) and creates the `optionwise`
    role/database if missing, so an unattended session doesn't need a human to have
    started anything. It also bootstraps `apps/web/.env` from `.env.example` if
    missing. This sandbox has Postgres 16 installed as a local service in addition to
    (an unusable) Docker daemon — that's what `ensure-db.sh` actually exercises here.
- **AI service** (`services/ai`): does not exist yet. Per `SPEC.md` it should be a
  separate Python FastAPI + LangGraph service, scaffolded in its own later task ("AI
  counsellor" section of `TASKS.md`). Python 3.11 and Docker are available in this
  environment.
- **Root tooling**: a root `package.json` (private, no deps of its own) exposes
  `dev` / `build` / `lint` / `typecheck` / `test` scripts that delegate to `apps/web`
  via `pnpm --filter web`. The `Makefile` wraps those (see below) and adds `make seed`,
  which now runs the real ingestion pipeline (`apps/web/prisma/seed.ts`) — see the
  Task 5 notes below.

## How to run

```bash
pnpm install      # or: make install
make dev          # starts the Next.js dev server (apps/web), http://localhost:3000
make check        # lint + typecheck + test — must pass before any task is "done"
make test         # tests only
make seed         # ingest data/raw/*.pdf, or write a small fake sample dataset if none
```

Node 22, pnpm 10, Python 3.11, and Docker are available in this environment.
`pnpm-lock.yaml` is committed at the repo root (the single lockfile for the whole
workspace) — `apps/web` does not have its own.

## Task 5 (Ingestion) notes

- `apps/web/lib/ingestion/` — `extractPdfText.ts` (thin `pdf-parse` v2 wrapper),
  `parseCutoffRows.ts` (pure text→rows parser, no I/O), `sampleDataset.ts` (the fake
  fallback data), `ingest.ts` (`ingestFromRawDir`: lists `data/raw/*.pdf`; if there are
  none, upserts the sample dataset with `isSample:true`; if there are, extracts +
  parses + upserts each with `isSample:false`, `source` set to the PDF's relative
  path). `apps/web/prisma/seed.ts` runs it via `make seed` and writes
  `data/ingestion-report.json` (gitignored — it's generated output).
- **The parsed text format is an invented placeholder, not derived from a real KEA
  PDF** — none was available to inspect (same root cause as `config/categories.json`'s
  UNVERIFIED status; see `BLOCKED.md`). `parseCutoffRows.ts` expects lines like
  `# year: 2024 round: 1` followed by
  `COLLEGE_CODE|COLLEGE_NAME|COURSE_CODE|COURSE_NAME|CATEGORY_CODE|CLOSING_RANK`. When
  a real KEA cutoff PDF is available, check what `extractPdfText` actually produces
  from it and adjust the parser to match — it will almost certainly need changes (real
  KEA PDFs are tables, and pdf-parse's text extraction of tables can be irregular).
  `data/raw/*.pdf` files are gitignored (source data, not code) — see
  `data/raw/README.md`.
- Tests use real fixtures, not mocks: `parseCutoffRows.test.ts` tests the pure parser
  against inline text; `extractPdfText.test.ts` and `ingest.test.ts` generate an actual
  small PDF at test time with `pdfkit` and round-trip it through the real `pdf-parse`
  library — this caught two real bugs before they'd have hit a real PDF: pdfkit
  wrapping a too-long line onto two lines (fixed with a wide custom page size, see
  `apps/web/lib/ingestion/__tests__/testHelpers.ts`), and pdf-parse's default
  `"-- page N of M --"` page-boundary marker being mistaken for a malformed data line
  (fixed by passing `pageJoiner: ""`).
- `vitest.config.ts` now sets `test.fileParallelism: false`. DB-backed test files each
  `TRUNCATE` the same real Postgres tables in `beforeAll`/`afterEach`; running files in
  parallel (Vitest's default) raced those truncates against each other and caused
  intermittent failures unrelated to the code under test. Worth revisiting (e.g. a
  per-file schema or transaction-per-test) if the test suite's DB-backed portion grows
  large enough that sequential execution becomes slow.
- Prisma writes in `ingest.ts` are per-row upserts in a loop, not batched — fine at
  today's scale (a handful of rows) but revisit if/when real KEA PDFs bring thousands
  of rows per file.

## Core predictors: Rank predictor notes

- `apps/web/lib/predictors/rankPredictor.ts`: `calculateMeritScore` (KCET marks /180
  scaled to 0-100, weighted 50/50 with board PCM% per `config/rankPredictor.json`),
  `interpolateRank` (piecewise-linear over configured score→rank points, clamped —
  never extrapolates past the configured range), `predictRank` (always returns
  optimistic/likely/conservative + a `"low"|"medium"` confidence, per SPEC.md — never
  a single number). `confidence` is `"low"` only when the merit score falls outside
  the configured point range (clamped); it's `"medium"`, never `"high"`, otherwise —
  deliberately, since the underlying `scoreRankPoints` are fabricated placeholder data
  (see below), so nothing here should claim high confidence yet. Every prediction also
  carries `basedOnSampleData: true` for the same reason, mirroring the DB-level
  `isSample` concept for this config-driven (non-DB) predictor.
- **`config/rankPredictor.json` is UNVERIFIED**, same as `config/categories.json` —
  see `BLOCKED.md`. The 50/50 weighting and 180-mark KCET scale are a reasonable
  reading of SPEC.md's own description; `scoreRankPoints` (the curve the predictor
  interpolates over) are entirely fabricated round numbers, not real historical KCET
  results. Replace both once a real KEA document / real historical data exists.
- Property-tested with `fast-check` (`rankPredictor.property.test.ts`, 500 runs each):
  a strictly higher merit score never yields a strictly worse likely rank, and
  optimistic ≤ likely ≤ conservative always holds, across randomized KCET-marks/board%
  inputs — not just the handful of example-based unit tests.
